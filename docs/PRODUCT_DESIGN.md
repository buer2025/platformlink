# PlatformLink 产品设计 v0.1

> 一句话定位：把 Agent 接进「客户群 ↔ 我方 ↔ 供应商群」这张关系网，让故障排查、问题转交、催量都能自动完成、可追踪，而且回复带有每个群自己的说话风格。

---

## 1. 背景与目标

我们是模型 API 的聚合方（例如 Seedance 等模型），上游对接多家**供应商**，下游服务多家**客户**，日常沟通都在 IM 群里：

- 客户在群里报问题（调用报错、429 限流、延迟高……），需要人工排查、判断责任方、来回转述。
- 问题属于供应商时，要去对应供应商群里描述、@ 人、跟进，进度容易断。
- 客户 429 多时要去供应商群催量。手工催量既重复，又容易显得机械。

**目标**

| 目标 | 衡量指标 |
|---|---|
| 缩短客户问题的首次响应时间 | 首响时间 P50 < 2 分钟 |
| 自动判断责任方（客户 / 我方 / 供应商） | 归因准确率 ≥ 85%，人工复核后可迭代 |
| 供应商问题全程可追踪、不丢单 | 转交工单闭环率 100%，超时自动催办 |
| 催量消息自然、个性化 | 供应商群反馈“像机器人”的次数接近 0 |

**非目标（v1 不做）**：替代工单系统、对客户自动退款或赔付、Agent 未经确认就对外发送敏感结论。

---

## 2. 核心概念

| 概念 | 说明 |
|---|---|
| **群（Group）** | 接入的 IM 群，类型为 `客户群` / `供应商群` / `内部群` |
| **主体（Party）** | 群背后的公司：客户或供应商。一个主体可以有多个群 |
| **标记（Tag）** | 给群或主体打的标识，分三类，见 §3 |
| **事件（Incident）** | Agent 从消息里识别出的一个问题，例如 “Seedance 调用 500” |
| **排查（Investigation）** | Agent 针对事件执行的诊断过程，结论为责任方加证据 |
| **转交单（Ticket）** | 发往供应商群的问题单，需要追踪到闭环 |
| **催量任务（Quota Push）** | 针对某个供应商、某个模型的扩容或催量请求 |
| **话术模板（Playbook）** | 我方发布的“意图”，例如催量要点。Agent 会结合群的风格改写后再发送 |

## 3. 群标记体系（个性化的基础）

标记是整个产品的核心资产，决定了 Agent “对谁、说什么、怎么说”。

### 3.1 业务标记（决定路由）
- 主体：`客户:XX公司` / `供应商:YY云`
- 涉及模型：`model:seedance`, `model:xxx`（供应商群标注它提供哪些模型，用于把问题路由到正确的供应商）
- 等级：`VIP` / `KA` / `普通`；`主力供应商` / `备用供应商`
- 默认对接人：群内的关键人（技术对接、商务对接），用于 @

### 3.2 风格标记（决定语气）
- 称呼习惯：例如 “X 总”、“哥”、“老师”、英文名
- 语气：`正式` / `轻松` / `熟络` / `英文`
- 表情与口头禅：是否用表情，常用词（例如 “辛苦啦”、“麻烦看下”）
- 禁忌：例如不提竞品、不在群里谈价格
- **风格样本**：从历史聊天中自动提炼的若干条“我方在该群的典型发言”，作为改写参考（可人工增删）

### 3.3 策略标记（决定自动化程度）
- `自动回复` / `需人工确认后发送` / `只观察不发言`
- 免打扰时段，例如供应商群夜间不催
- 催量频率上限，例如同一供应商 4 小时内最多催 1 次

> 标记可以手动打，也可以由 Agent 根据历史消息**建议**，人工确认后生效。

## 4. 核心流程

### 4.1 客户报障 → 排查 → 分流

```
客户群消息
   │
   ▼
[消息监听] ──► [意图识别] 是否为问题？是哪个模型、什么错误码、请求 ID？
   │
   ▼
创建 Incident（自动回复客户：“收到，正在排查”，带客户群风格）
   │
   ▼
[排查 Agent] 调用工具：
   · 查调用日志（按客户 key / request_id / 时间窗）
   · 查错误码分布、该模型整体成功率
   · 查供应商状态页、近期变更
   · 用相同参数复现调用
   │
   ▼
得出结论：责任方 + 证据 + 置信度
   ├─ 客户侧问题（参数错误、余额不足、key 失效…）
   │     → 生成解释和修复建议 → 回复客户（引用原消息）
   ├─ 我方问题 → 通知内部群和值班人
   └─ 供应商问题
         → 按 model 标记找到供应商群
         → 生成转交单，在供应商群 @ 对接人，附错误样例和时间
         → 回复客户：“已定位为上游问题，正在协调处理”
```

**关键点**
- 所有对外消息都走 **§4.4 预发机制**：Agent 给出准确率评分，进入预发队列，管理员不干预时到时自动发送。
- 多个客户同时报同一类错误时，合并成一个 Incident，避免向供应商重复发单。

### 4.2 供应商转交单追踪

- 状态：`已发送 → 已读/已回复 → 处理中 → 已解决 → 已同步客户`
- **回复识别**：供应商在群里引用了我们的消息，或 @ 我方账号时，自动关联到对应转交单；Agent 判断回复内容属于“确认收到 / 已修复 / 需要更多信息”。
- **超时催办**：例如 30 分钟无回复，就用该群的风格再 @ 一次；仍无回复则升级到内部群，提醒人工电话联系。
- **闭环**：供应商说已修复后，Agent 自动复测；复测通过就在客户群引用最初的报障消息，回复“已恢复”。

### 4.3 429 催量

触发方式：
1. **被动**：客户群反馈 429 多，或监控发现某模型 429 比例超过阈值。
2. **主动**：运营在后台发布一条**催量意图**，例如 “Seedance 明天活动，需要 RPM 从 500 提到 2000”。

执行：
- Agent 按 model 标记筛出相关供应商群，结合**风格标记和风格样本**，为每个群生成不同措辞的催量消息。
- 消息带上数据支撑（当前 429 比例、近期用量曲线），比空口催更有说服力。
- 防机械感：
  - 每个群的消息不同，同一群前后两次也不重复（与历史发言做相似度去重）
  - 随机化发送时间，避开免打扰时段
  - 可以先说一句寒暄或接续上次话题，再讲正事
- 默认**人工预览后批量发送**；信任度高的群可以开启自动发送。
- 供应商回复，例如“已扩到 1500”，会被结构化记录下来，回填到配额看板。

### 4.4 预发机制（准确率判断 + 超时自动执行）

Agent 生成的每条对外消息都附带**准确率评分**（0–100），依据包括：证据是否充分（是否查到 request_id 日志、能否复现）、与历史案例的相似度、分类模型的置信度。

```
生成消息 + 准确率评分
   │
   ▼
进入预发队列，通知管理员（内部群卡片 + 后台），卡片提供 [立即发送] [修改] [取消]
   │
   ├─ 管理员操作 → 按操作执行
   └─ 倒计时结束无人操作 → 自动发送
```

倒计时按评分和群标记分档（默认值，可在后台配置）：

| 准确率 | 默认行为 |
|---|---|
| ≥ 90 | 预发 2 分钟后自动发送 |
| 70–89 | 预发 10 分钟后自动发送 |
| < 70 | 不自动发送，必须人工确认（超时则升级提醒） |

- 群标记可以覆盖默认规则，例如 VIP 群一律加长倒计时，`只观察` 群永不自动发送。
- “收到，正在排查”这类低风险安抚消息可以设为 0 秒直接发送。
- 管理员的修改和取消会记录为反馈，用于校准评分。

## 5. 功能模块

| 模块 | 功能 |
|---|---|
| **群接入** | 绑定 IM 账号或机器人，同步群列表，选择要监控的群 |
| **标记中心** | 给群和主体打标记、编辑风格样本、AI 推荐标记 |
| **消息流** | 按群和主体查看消息，高亮 Agent 识别出的问题 |
| **事件中心** | Incident 列表、排查过程（工具调用与证据）、结论复核 |
| **转交单看板** | 供应商单的状态、超时情况、各供应商响应时效统计 |
| **催量中心** | 发布催量意图 → 预览各群改写结果 → 发送 → 追踪回复 |
| **预发队列** | 所有待发送的对外消息，显示准确率和倒计时，支持立即发送、修改、取消 |
| **知识库** | 错误码说明、各模型的常见问题、历史排查案例（供 Agent 检索） |
| **团队与权限** | 多名技术支持协作：角色权限、群负责人分配、值班与通知路由（见 §5.1） |
| **审计日志** | Agent 发出的每条消息、依据了什么数据，全部可追溯 |

### 5.1 多人协作（群多、技术支持多）

- **角色**：`管理员`（全局配置、标记规则、自动化阈值）/ `技术支持`（处理负责群的预发、事件、转交单）/ `只读`
- **群负责人**：每个群指定主负责人 + 备份负责人；预发卡片和超时提醒**只推给该群负责人**，避免所有人被刷屏
- **值班表**：非工作时间推给值班人；负责人不在时自动转给备份
- **认领与锁定**：一个事件 / 预发消息被某人点开处理时加锁，防止两人同时回复客户
- **个人工作台**：“我负责的群”、“待我确认的预发”、“我跟进的转交单”
- **批量操作**：批量打标记、批量分配负责人、按标记筛选群（群数量多时必需）
- **技术支持本人在群里发言**：系统识别为我方人员，Agent 不再重复回复，并把该发言关联到对应事件

## 6. 系统架构（建议）

```
IM 平台（企业微信 / 飞书 / Telegram）
        │  Webhook / 长连接
        ▼
 ┌──────────────┐     ┌──────────────┐
 │ IM 适配层     │◄───►│ 预发队列      │（准确率分档、倒计时、限速、免打扰）
 └──────┬───────┘     └──────────────┘
        ▼
 ┌──────────────┐
 │ 消息总线      │
 └──────┬───────┘
        ▼
 ┌────────────────────────────────────┐
 │ Agent 编排层                        │
 │  · 分类 Agent（是否问题、类型）       │
 │  · 排查 Agent（调用工具）             │
 │  · 话术 Agent（风格化改写）           │
 │  · 跟进 Agent（转交单、回复识别）     │
 └──────┬─────────────────────────────┘
        ▼
 工具：日志查询 / 监控指标 / 复测调用 / 供应商状态 / 知识库检索
        ▼
 数据：群、标记、事件、转交单、催量任务、消息存档（PostgreSQL + 向量库）
```

- **IM 适配层**做抽象，让业务层与具体 IM 平台解耦。首批接入三个平台：
  - **企业微信**：自建应用 + **会话内容存档**（已确认可开通），用于拉取外部群消息；发送走应用 / 群机器人
  - **飞书**：自建应用机器人，事件订阅接收群消息，支持 @ 和引用回复
  - **Telegram**：Bot API，需在 BotFather 关闭 privacy mode 才能收到群内全部消息
- **日志查询**：我方有专门的日志数据库，支持按 request_id 查询；具体查询方式待提供，排查 Agent 通过一个 `query_log(request_id)` 工具接入。
- **对外发送统一走发送队列**：限速、审批、免打扰、去重全部集中在这里，是防止 Agent 乱发消息的总闸。
- 后台用 Web 管理端。

## 7. 风险与对策

| 风险 | 对策 |
|---|---|
| Agent 误判责任方，甩锅给供应商或客户 | 置信度阈值 + 人工确认；对外措辞中性；结论附证据 |
| 发错群、泄露信息（把 A 客户的信息发进 B 群） | 发送前校验：消息中的主体必须与目标群主体一致；敏感字段脱敏 |
| 催量频繁引起反感 | 频率上限、免打扰、风格化、人工预览 |
| IM 平台风控封号 | 优先使用官方机器人 API；控制发送频率 |
| 风格提炼不准 | 风格样本可人工维护，支持“像不像”的反馈回路 |

## 8. 版本规划

**MVP（v0.1，约 4–6 周）**
- 接入企业微信、飞书、Telegram（建议先 Telegram/飞书跑通，再接企业微信）
- 群绑定 + 标记（手动）
- 客户报障识别 → 排查（request_id 日志查询 + 复测）→ 预发机制 → 回复或转交
- 转交单基础追踪（引用 / @ 识别 + 超时提醒）

**v0.2**
- 催量中心（意图发布 → 风格改写 → 预览发送）
- 风格样本自动提炼、AI 推荐标记
- 同类问题合并

**v0.3+**
- 高信任群开启全自动
- 供应商响应时效评分，作为路由和商务谈判依据
- 更多 IM 平台（钉钉等）
