# 路线图（自检后的差距清单）

对标 Intercom Fin、Zendesk、Front、Chatwoot 等成熟客服产品，按优先级排列。

## 已完成（自检轮）

- 同群消息串行处理，连发 / 并发不会互相覆盖
- 处理出错兜底：记到事件并 @ 负责人
- 从人工修改中学习：AI 原稿 → 同事改法，用于该群后续所有改写
- 数据看板：首次响应、解决用时、AI 原稿采用率、人工修改、升级、正在等回复的客户
- 截图识别：客户发报错截图，自动摘录报错与 request_id

## 下一步

| 优先级 | 项目 | 说明 |
|---|---|---|
| P0 | 每人独立账号与权限 | 现在共用一个 ADMIN_TOKEN，无法区分是谁操作；需要登录、角色（管理员 / 支持）、操作留痕 |
| P0 | 事件指派与值班 | 事件指派给具体同事；按值班表 / 群负责人自动分配；升级时 @ 当班的人 |
| P0 | 企业微信发送、飞书加密 | 企业微信客户群发消息受平台限制（需评估「群机器人 / 应用消息 / 会话存档 + 人工」方案）；飞书事件加密需支持 |
| P1 | SLA 告警 | 客户等待超过阈值主动提醒（内部群 / 手机推送），按客户等级区分 |
| P1 | 工作时间 | 非工作时间的回复策略（如告知响应时间、只处理紧急问题） |
| P1 | 评估集 | 从真实事件挑几十个做回归集，改提示词 / 换模型时量化对比 |
| P1 | 催量中心 | 按供应商汇总 429 与用量需求，统一跟进额度 |
| P2 | 飞书 / 企业微信截图识别 | 目前只实现了 Telegram 的图片下载 |
| P2 | 多进程部署 | 调度器与按群串行锁目前依赖单进程；扩容需换成数据库锁 / 队列 |
| P2 | 长对话压缩 | 单个事件内消息很多时压缩历史 |
