# 路线图（自检后的差距清单）

对标 Intercom Fin、Zendesk、Front、Chatwoot 等成熟客服产品，按优先级排列。

## 已完成（自检轮）

- 同群消息串行处理，连发 / 并发不会互相覆盖
- 处理出错兜底：记到事件并 @ 负责人
- 从人工修改中学习：AI 原稿 → 同事改法，用于该群后续所有改写
- 数据看板：首次响应、解决用时、AI 原稿采用率、人工修改、升级、正在等回复的客户
- 截图识别：客户发报错截图，自动摘录报错与 request_id

## 已完成（P0）

- 每人独立账号：用户名密码登录（scrypt），管理员 / 技术支持两种角色，所有操作记在本人名下；管理口令保留为内置超级管理员
- 事件指派与值班：群负责人优先，否则分给值班中、手上未结事件最少的人；认领 / 改派；「我的」事件；升级时 @ 被指派人
- 企业微信：群机器人 Webhook 发送（内部群）；外部客户群受平台限制，走人工确认
- 飞书：支持 Encrypt Key（事件解密 + 签名校验）；图片与富文本消息（含截图识别）

- SLA 提醒：客户等待超阈值（群可单独设置）在内部群 @ 负责人；工作时间外阈值放宽、只提醒值班的人
- 评估集：`uv run python -m evals.run`，首轮 92% → 修正提示词后 100%

- 催量中心：按供应商汇总未解决的限流 / 用量事件与日志库 24h 429；AI 带真实数字、按供应商群风格起草催量（人工确认）；堆积时自动起草，2 小时冷却

## 已完成（P2 · 扩展性与对话质量）

- 多进程 / 多副本部署：数据库租约锁（SQLite / PostgreSQL 通用）替代进程内锁——调度器自动选主、主挂了自动接管；Telegram 轮询只由一个进程负责；同群消息跨进程严格串行；卡住的发送只按认领时间恢复，不误伤其他进程。已用 3 个 worker + PostgreSQL 并发实测：6 条同群消息合并成 1 个事件、1 条最终回复
- 长对话压缩：单个事件超过 24 条或 6000 字时，较早消息增量压成摘要（保留全部 request_id / 模型 / 报错码），最近 12 条原话逐字保留；攒够 10 条才重新压缩
- 没有进行中问题时客户招呼（「在吗」）立即回应；一般咨询先查知识库，有依据 10 分钟倒计时，没依据只说「帮您确认」并等人工
- 评估集 25 → 44 条（开口判断、引用判断、压缩不丢信息等），100% 通过；评测发现结构化输出里带默认值的字段模型常省略，已改为必填

- 接入 Jev 结构化决策（AGTCloud `/v1/decisions`）：分诊与「要不要回」先走 Jev（中位数约 160ms，Claude 约 2.9s），有把握时直接采用，拿不准 / 失败回退 Claude；对比评测 `uv run python -m evals.jev_compare`：jev-1.14.0 30/30，jev-1.13.0 29/30

- 模型调用全量留存：所有 Claude / Jev 调用（输入、输出、耗时、token、成功/失败、所属群 / 事件 / 触发消息）写入 `model_calls`；后台批量异步落库，不拖慢回复；「模型调用」页可筛选、看原文，事件抽屉内可看该事件的全部调用
- 处理进度实时可见：事件抽屉顶部显示「收到消息 → 分诊 → 排查 → 回复客户 → 转交供应商 → 解决」，处理中每秒刷新，显示正在调用的模型与 Agent 第几轮；排查每一步即时提交，时间线同步实时更新

- 证据清单：排查前自动核对 request_id（含模糊匹配）、报障前后时段的客户日志、客户说的错误码与日志是否一致、同渠道同时段其他客户（横向对比）、渠道实测（配置 new-api 管理接口后）、历史经验；Agent 据此补证据，准确率按证据封顶（有矛盾 ≤70，单项直接证据 ≤80）；事件详情展示清单。日志时间统一按业务时区显示

- 操作审计：后台所有写操作、登录（含失败尝试）、权限拒绝、出错请求，平台回调、Agent 处理每条群消息、定时任务（自动发送、催办、SLA、自动关闭、清理）、服务启动 / 停止 / 调度器接管全部留痕——操作者、IP、参数（密码密钥打码）、结果、耗时、其间 SQL 条数与数据库耗时；「操作审计」页仅管理员可见
- 数据库查询耗时：new-api 日志库的每一次查询单独记录（语句、参数、耗时、行数、发起函数、所属事件），业务库记录超过 `SLOW_QUERY_MS` 的慢查询；统计 P50 / P95 / 最慢与最耗时的调用方，事件抽屉可看该事件查了哪些日志
- 记录保留期：`RECORD_RETENTION_DAYS`（默认 0 永久保留）统一清理审计、查询与模型调用记录
